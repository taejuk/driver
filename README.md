# 가상 가속기 드라이버 프로젝트 로드맵

> QEMU 가상 가속기 디바이스 모델 + `drivers/accel` 최소 드라이버
> 목표: 하드웨어 없이 가속기 드라이버를 처음부터 끝까지 설계·구현한 경험 확보

---

## 0. 이 로드맵의 원칙

**각 마일스톤은 판정 가능한 완료 조건을 하나씩 갖는다.**
"이해했다", "익숙해졌다"는 완료 조건이 될 수 없다. `/proc/interrupts` 카운트가 증가했는가,
kmemleak이 조용한가 같은 관측 가능한 사실만 완료 조건으로 인정한다.

**버티컬 슬라이스 우선.**
레이어를 아래부터 쌓아 올리지 않는다. 매 마일스톤마다 디바이스 → 드라이버 → 유저스페이스가
얇게나마 연결된 상태를 유지한다.

**명세를 얼린 뒤 드라이버를 맞춘다.**
디바이스를 직접 만들기 때문에, 드라이버가 안 맞으면 디바이스를 고쳐버리는 유혹이 생긴다.
그 순간 "하드웨어 제약"이라는 개념이 사라지고 프로젝트의 가치가 증발한다.
명세 변경은 허용하되, **변경 이유를 문서에 기록**하는 것을 규칙으로 한다.

**디버그 빌드와 성능 빌드를 처음부터 분리한다.**
`CONFIG_PROVE_LOCKING`은 오버헤드가 크다. M5에서 급하게 나누지 말고 M0부터 두 개의
커널 config를 유지한다.

## M0 — 살아 있는 핑퐁

**기간 목표**: 1주
**목적**: QEMU 빌드–부팅–모듈 로드 사이클을 몸에 붙인다

### 디바이스 (`hw/misc/nacc.c`)

`hw/misc/edu.c`를 복사해 시작하되, 기능을 **덜어내는** 방향으로 간다.

| 남길 것 | 뺄 것 |
|---|---|
| PCI 디바이스 등록 (`pci_device_class_init`) | factorial 계산 로직 |
| BAR0 MMIO 영역 | 내장 DMA 엔진 |
| MSI-X 벡터 1개 | 워커 스레드 / 뮤텍스 |

레지스터는 4개만 정의한다.

| 오프셋 | 이름 | 접근 | 설명 |
|---|---|---|---|
| 0x00 | `ID` | RO | 매직값. 드라이버가 프로브 시 확인 |
| 0x08 | `IRQ_STATUS` | RO | 인터럽트 원인 비트맵 |
| 0x10 | `IRQ_ACK` | WO | 쓰면 해당 비트 클리어 |
| 0x18 | `DOORBELL` | WO | 쓰면 즉시 인터럽트 발생 |

> edu 디바이스는 0x80 미만 영역에 4바이트 접근 제한이 있으나, 이건 edu의 선택이지
> 하드웨어 제약이 아니다. 자기 디바이스이므로 처음부터 8바이트 정렬·8바이트 접근으로
> 통일하는 편이 이후 혼란이 적다.

### 드라이버

probe / remove / ISR만 있는 100줄 내외 모듈. GEM도 IOCTL도 아직 없다.
char device조차 만들지 않는다 — 유저스페이스는 `/sys/bus/pci/devices/.../resource0`를
mmap해서 직접 두드린다.

### 완료 조건

유저스페이스에서 `DOORBELL`에 쓰면 `/proc/interrupts`의 해당 항목 카운트가 1 증가한다.

### 부수 작업

- 커널 config 2벌 확정: `debug`(PROVE_LOCKING, DEBUG_ATOMIC_SLEEP, KMEMLEAK, DYNAMIC_DEBUG)
  / `perf`(디버그 옵션 전부 off)
- busybox initramfs + 9p virtio 공유 디렉터리 구성 (모듈 재컴파일 후 재부팅 없이 반입)
- 부팅 스크립트 1개로 `make → qemu 실행 → insmod`까지 자동화

## M0.5 — 명세를 얼린다

**기간 목표**: 2~3일
**목적**: M1 코드를 쓰기 전에 계약을 확정한다

`docs/nacc-spec.md`를 작성한다. 항목:

1. **레지스터 맵** — 오프셋, 폭, RO/WO/RW, 리셋값, 접근 정렬 요구
2. **디스크립터 포맷** — 필드별 비트 위치, 정렬 요구, 최대 전송 크기, 예약 필드 규칙
3. **커맨드 링 / 컴플리션 링** — 크기, head/tail의 소유자(호스트 vs 디바이스),
   랩어라운드 규칙, full/empty 판별 방법
4. **상태 전이** — IDLE → RUNNING → ERROR, 각 전이의 유발 조건과 관측 방법
5. **메모리 순서 규칙** — 호스트가 디스크립터를 쓴 뒤 doorbell을 치기 전에
   무엇이 보장돼야 하는가. 디바이스가 컴플리션을 쓴 뒤 MSI-X를 쏘기 전에는?

### 5번이 이 마일스톤의 핵심

xdma 분석에서 도달한 **"소유권과 순서 규칙은 struct 정의로 표현할 수 없다"**는 결론을,
이번에는 자기 손으로 산문으로 써본다. 여기서 쓴 문장 하나하나가 M1에서
`dma_wmb()` / `smp_store_release()` 배치의 근거가 된다.

읽는 쪽이 아니라 **쓰는 쪽**에서 같은 문제를 만나는 것이 이 프로젝트의 목적 중 하나다.

### 완료 조건

이 문서만 보고 제3자가 드라이버를 작성할 수 있는 수준.
판정이 애매하면 — 일주일 뒤 다시 읽었을 때 모호한 지점이 없으면 통과.

## M1 — 커맨드 링 (본론)

**기간 목표**: 2~3주

### 디바이스

- 호스트 메모리에서 DMA로 디스크립터를 읽는다 (`pci_dma_read`)
- 처리한다 — 연산 내용은 중요하지 않다. `memcpy` 또는 바이트 단위 변환으로 충분하다.
  **사각형 하나 그리는 것보다 링 프로토콜이 정확한 것이 100배 중요하다**
- 컴플리션 링에 결과를 쓴다 (`pci_dma_write`)
- MSI-X를 쏜다

### 드라이버

- 링 버퍼 할당 (`dma_alloc_coherent`)
- 디스크립터 작성 → 배리어 → doorbell
- ISR에서 컴플리션 링 소비 → 완료 통지

### 여기서 재사용되는 xdma 분석 자산

| xdma에서 얻은 것 | M1에서의 적용 |
|---|---|
| 디스크립터 수명 관리 | 링 슬롯의 소유권 전환 지점을 직접 정의 |
| 완료 통지 경계 | ISR에서 어디까지 하고 어디부터 미룰지 결정 |
| `vc->lock` 단일 경계 | 자기 드라이버의 락 경계를 처음부터 설계 |
| CAT3 락 계약 | 자기 헬퍼에는 `lockdep_assert_held()`를 처음부터 넣는다 |

**차이점**: xdma에서는 "왜 이 필드가 여기 있는가"를 추론해야 했다.
이번엔 자기가 정했으므로 답을 안다. 그리고 그 결정이 좋았는지 나빴는지도 알게 된다.

### 완료 조건

- 1000개 디스크립터를 연속 제출하고 전부 완료 통지를 받는다
- 링 랩어라운드가 최소 2회 발생한다
- kmemleak 무경고, lockdep splat 없음

## M2 — accel 서브시스템으로 승격

**기간 목표**: 3~4주

M1까지는 자작 char device로도 가능하다. 여기서부터 프레임워크에 올린다.

- DRM 디바이스 등록 (`drm_accel` 계열 초기화)
- GEM 버퍼 오브젝트 — 할당, 참조 카운트, 소멸
- IOCTL 커맨드 서브밋 — 유저가 GEM 핸들을 넘기면 드라이버가 링 디스크립터로 변환
- mmap으로 GEM 버퍼를 유저스페이스에 노출

### 참조 드라이버

- `drivers/accel/qaic/` — 구조가 잘 정리돼 있다
- `drivers/accel/amdxdna/` — Lizhi Hou가 추가. XDMA → 가속기 궤적과 직접 겹친다

> 주의: 이 둘은 "읽고 이해할 대상"이 아니라 **옆에 놓고 참조할 대상**이다.
> M1을 직접 만든 뒤에 보면 "왜 이렇게 했는지"가 보인다. 순서를 뒤집지 말 것.

### 완료 조건

유저스페이스 테스트 프로그램이 GEM 버퍼를 할당 → 데이터 write → IOCTL 서브밋 →
완료 대기 → 결과 read 까지 수행한다.

## M3 이후 — 모듈식 확장

여기서부터는 **순서가 고정되지 않는다.** 관심사나 지원하려는 회사의 스택에 따라 고른다.

### M3a. 펌웨어 로딩 + 부트 시퀀싱
`request_firmware()`, 상태 머신 기반 부팅, 타임아웃 처리.
리벨리온 스택이 펌웨어를 쓰므로 우선순위가 높다.

### M3b. dma-buf export/import
다른 디바이스와 버퍼 공유. 가속기 드라이버의 실질적 필수 기능.

### M3c. 디바이스 리셋 / FLR
in-flight 커맨드 정리가 핵심. **xdma의 `xdma_terminate_all` splice 패턴 의문이
여기서 다시 등장한다** — 이번엔 자기가 설계자이므로 답을 정할 수 있다.

### M3d. hwmon 텔레메트리 + netlink 비동기 이벤트
리벨리온의 RSMD 데몬 구조와 대응된다.

### M3e. VFIO 패스스루
가장 나중. 앞의 것들이 안정된 뒤.

## 병행 트랙

프로젝트와 별개로 계속 굴려야 하는 것들.

### 업스트림
- `dma_get_slave_caps()`의 `directions` 필드 누락 → `-ENXIO` 버그
  - **선행 조건**: 연구소의 오픈소스 기여 정책 확인. 이게 먼저다
  - `checkpatch.pl --strict`, `get_maintainer.pl`, `b4` 워크플로 숙달
  - Cc 후보: Lizhi Hou (AMD)
- virt-dma CAT3 헬퍼에 `lockdep_assert_held()` 추가 — M1에서 자기 드라이버에
  적용해본 뒤 제안하면 근거가 생긴다

### libxdma.c (멘토 할당분)
비교 축을 고정하고 읽는다: 디스크립터 수명 / 락 경계 / 완료 통지 / 에러 처리.
"xdma.c가 프레임워크에 위임한 것을 libxdma는 어디서 직접 하는가"가 유일한 질문.
결과물은 매니저의 "커널 API 표준화" 목표에 대한 직접적 답변이 된다.

### 미해결 질문
`git log -S` / lore 아카이브 조사. 코드를 더 읽어서 나올 답이 아니다.
- `XDMA_DESC_BLEN_MAX`가 `PAGE_SIZE`를 정확히 차감하는 이유
- `xdma_terminate_all`의 비표준 splice 패턴
- 미사용 `CHAN_CTRL_POLL_MODE_WB`

## 리스크와 대응

| 리스크 | 신호 | 대응 |
|---|---|---|
| M1에서 링 프로토콜을 계속 고침 | 명세 문서가 주 2회 이상 바뀜 | 변경 이유를 문서에 기록하는 규칙 강제. 기록이 부담되면 자연히 줄어든다 |
| QEMU 디바이스 쪽에 시간을 과소비 | 연산 로직을 정교하게 만들고 있음 | 연산은 `memcpy`면 충분하다는 원칙 재확인 |
| accel 참조 드라이버를 먼저 읽고 압도됨 | M1 전에 qaic을 정독하고 있음 | M2 전까지 열지 않는다 |
| 정적 분석 습관으로 회귀 | 코드는 읽는데 부팅은 안 함 | 매 마일스톤 완료 조건이 관측 가능한 사실인지 재확인 |

## 확인이 필요한 사항

이 로드맵에서 **검증되지 않은 전제**를 명시한다.

1. **메인라인 QEMU에 Xilinx XDMA 엔드포인트 모델이 있는지 확인하지 못했다.**
   있다면 xdma 고유 가설(BLEN_MAX, terminate_all)도 런타임 검증이 가능해진다.
   없다면 실물 FPGA 접근이 유일한 경로다.
2. **리벨리온의 채용 기준에서 "end-to-end 설계 경험 > 업스트림 커밋 수"라는 판단은 추론이다.**
   확인된 사실이 아니다. 다만 어느 쪽이든 이 프로젝트의 가치가 훼손되지는 않는다.
3. **각 마일스톤의 기간은 근거 있는 추정이 아니다.** M0를 끝낸 뒤 실측으로 재조정할 것.
4. **연구소의 오픈소스 기여 정책을 아직 확인하지 않았다.** 업스트림 트랙의 선행 조건.
