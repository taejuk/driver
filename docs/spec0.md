# nacc 디바이스 명세서

| 항목                 | 값                                |
| -------------------- | --------------------------------- |
| 문서 버전            | 0.3-draft                         |
| 대상 하드웨어 리비전 | 1                                 |
| 상태                 | M1 확정. QEMU 모델 구현 착수 가능 |
| 최종 수정            | TODO (작성일 기입)                |

> **작성 규칙 (문서 완성 후 삭제)**
>
> 이 문서는 **외부 벤더가 제공한 데이터시트**라고 가정하고 작성한다.
> 드라이버 구현 편의를 이유로 어떤 동작도 생략하지 않는다.
> "드라이버가 알아서 하면 된다"는 문장이 떠오르면, 그건 이 문서에
> 하드웨어 동작이 빠졌다는 신호다.
>
> QEMU 디바이스 모델은 이 문서를 따라 구현한다. 반대 방향은 금지한다.
>
> **본문에는 `dmesg`, 커널 함수명, `-ENODEV` 같은 소프트웨어 용어가
> 등장하지 않는다.** 단, `[SW]` 태그가 붙은 요구사항은 예외다.
> `[SW]`는 드라이버 측 규약을 기술하는 절이기 때문이다.

## §0. 문서 규약

### 0.1 요구 수준

RFC 2119를 따른다.

| 용어                | 의미                            |
| ------------------- | ------------------------------- |
| MUST / MUST NOT     | 위반 시 동작 미정의             |
| SHOULD / SHOULD NOT | 강한 권고. 위반하려면 근거 필요 |
| MAY                 | 선택 사항                       |

허용을 서술할 때는 MAY를 쓴다. "하지 않아도 된다"에 MUST를 붙이지
않는다 — MUST는 의무이지 허가가 아니다.

### 0.2 출처 태그

모든 요구사항에 아래 태그를 붙인다.

| 태그   | 의미                                             |
| ------ | ------------------------------------------------ |
| `[HW]` | 하드웨어가 강제하는 제약. 드라이버에 선택권 없음 |
| `[SW]` | 소프트웨어 규약. 다르게 설계할 수도 있었음       |

`[SW]` 항목에는 **왜 그렇게 정했는지 한 줄**을 반드시 덧붙인다.
근거를 못 쓰겠으면 그건 `[SW]`가 아니라 미결정 사항이다 → §9로 보낸다.

### 0.3 요구사항 ID

형식: `NACC-REQ-nnn` (3자리, 순번, 재사용 금지)

삭제된 요구사항은 번호를 비우지 말고 `(삭제됨: 사유)`로 남긴다.
드라이버 코드 주석과 테스트에서 이 ID를 참조한다.

```c
/* NACC-REQ-016: 디스크립터 쓰기가 doorbell보다 먼저 보이도록 보장.
 * writel()이 선행 메모리 쓰기의 완료를 기다리므로 추가 배리어는 없다.
 */
writel(prod, base + NACC_REG_RING_PROD);
```

**번호 사용 현황**

번호 블록은 v0.1에서 절별로 나눴으나 개정을 거치며 일부 어긋났다.
아래가 실제 상태이며, 새 번호는 "미사용" 구간에서 가져온다.
**어긋난 번호를 재정렬하지 않는다** — 재사용 금지 원칙이 우선한다.

| 구간        | 사용처                                 |
| ----------- | -------------------------------------- |
| `001`–`008` | §2 PCI 식별 및 자원                    |
| `009`       | 미사용                                 |
| `010`–`021` | §4 전역 접근 규칙                      |
| `022`       | 삭제됨 (§5.1)                          |
| `023`–`029` | §5 레지스터 (`ID` / `CTRL` / `STATUS`) |
| `030`–`046` | §6 커맨드 링                           |
| `047`–`049` | §7 인터럽트 모델                       |
| `050`–`051` | §8 오류 모델                           |
| `052`–`056` | v0.3 신규 (§3 / §4 / §6 / §7에 분산)   |
| `057`–`059` | 미사용                                 |
| `060`–`061` | §5 레지스터 (`ERR_CODE`)               |
| `062`–`066` | §7 인터럽트 모델                       |
| `067`–`069` | §8 오류 모델                           |
| `070`–`079` | §5 레지스터 (`RING_*`)                 |
| `080`–`089` | 미사용                                 |
| `090`–`098` | §3 상태 머신                           |
| `099`       | 미사용                                 |

### 0.4 레지스터 필드 속성

| 표기   | 의미                                |
| ------ | ----------------------------------- |
| `RO`   | 읽기 전용. 쓰기는 무시              |
| `RW`   | 읽기/쓰기                           |
| `RW1C` | 1을 쓰면 클리어. 0을 쓰면 변화 없음 |
| `WO`   | 쓰기 전용. 읽으면 0                 |
| `RSVD` | 예약. §4.4 정책 적용                |

### 0.5 비트 표기

- 비트 범위: `[31:24]` (MSB:LSB)
- 단일 비트: `[7]`
- 예약값: `0`
- 미정의: `X`

## §1. 범위

### 1.1 이 문서가 정의하는 것 (M1)

- PCI 식별자, BAR0 레이아웃, MSI 벡터 1개
- 6개 상태 디바이스 상태 머신 (`RESET`/`INIT`/`READY`/`BUSY`/`HALTING`/`ERROR`)
- 전역 접근 규칙: 접근 폭, 엔디안, 순서, 예약 필드, 미매핑 영역
- 레지스터 맵 11개 (오프셋 `0x0000`–`0x0043`)
- 호스트 메모리상의 단일 커맨드 링 (32바이트 디스크립터, 버스 주소 연속)
- opcode 2개: `NOP`, `MEMCPY`
- 완료/오류 인터럽트와 ack 프로토콜
- 오류 코드 6종 및 오류 시 링 상태
- `CTRL.ENABLE ← 0`에 의한 정지(quiesce) 시퀀스

### 1.2 이 문서가 정의하지 않는 것

명시적으로 범위 밖임을 선언한다. 나중에 자신과 논쟁하지 않기 위함이다.

| 항목                     | 도입 예정 | 비고                                      |
| ------------------------ | --------- | ----------------------------------------- |
| 펌웨어 로딩              | M2        | `STATUS.STATE` 인코딩 `6`–`7`을 예약해 둠 |
| 디바이스 로컬 메모리     | M2        | M1의 `MEMCPY`는 호스트→호스트만           |
| shadow index (writeback) | M2        | §9 Q7                                     |
| 다중 커맨드 링           | 미정      | M1은 링 1개로 고정                        |
| MSI-X                    | 미정      | M1은 MSI 1벡터 고정 (§9 Q3 결정)          |
| FLR / 디바이스 리셋      | M3        | §3.4의 quiesce 의미론을 그대로 승계       |
| hwmon 텔레메트리         | M3        |                                           |
| dma-buf import/export    | M3        |                                           |
| VFIO 패스스루            | M3+       | §2.2 BAR 크기 결정에 이미 반영            |

> **주의:** M3에서 추가할 기능이라도, **상태 머신에 자리를 비워둘지 여부**는
> 지금 결정해야 한다. 나중에 상태를 끼워넣으면 기존 전이가 전부 깨진다.
>
> M1의 결정: `STATUS.STATE`를 3비트로 두고 `0`–`5`만 사용한다.
> `6`–`7`은 M2 펌웨어 상태용으로 예약한다. 상태를 8개 넘게 쓰게 되면
> 필드 폭을 늘려야 하고, 그건 §2.4 "추가만 허용" 정책 위반이다.

## §2. PCI 식별 및 자원

### 2.1 식별자

| 항목        | 값       | 비고                                       |
| ----------- | -------- | ------------------------------------------ |
| Vendor ID   | `0x1234` | QEMU가 내부 테스트 디바이스에 쓰는 값      |
| Device ID   | `0x11EA` | edu 디바이스(`0x11E8`)와 구분              |
| Revision ID | `0x01`   | §2.4 참조                                  |
| Class Code  | `0x1200` | Processing Accelerator (§9 Q6 — 확인 필요) |

> **확인 필요:** `0x1234:0x11EA`는 PCI-SIG에 등록된 식별자가 아니다.
> QEMU 디바이스 모델 안에서만 유효하며, 실물 하드웨어에 쓰면 안 된다.
> Class Code `0x1200`이 리눅스 `PCI_CLASS_PROCESSING_ACCELERATOR`와
> 일치하는지는 `include/linux/pci_ids.h`에서 직접 확인할 것.

**NACC-REQ-001** `[SW]` 드라이버는 Vendor/Device ID가 위 값과 일치하는
함수에만 바인딩해야 한다(MUST).

> 근거: Class Code 매칭은 같은 클래스의 다른 디바이스까지 잡는다.

### 2.2 BAR 레이아웃

| BAR    | 크기   | 종류                          | 용도     |
| ------ | ------ | ----------------------------- | -------- |
| BAR0   | 4 KiB  | MMIO, 32bit, non-prefetchable | 레지스터 |
| BAR1~5 | 미사용 | —                             | —        |

**NACC-REQ-002** `[HW]` BAR0은 MMIO 공간이며 prefetchable이 아니다.

**NACC-REQ-003** `[HW]` BAR0의 크기는 4 KiB이다. 레지스터는 오프셋
`0x0000`–`0x0043`에만 존재하며, 나머지 영역은 §4.5의 미매핑 정책을 따른다.

> 근거(크기 선택): 정의된 레지스터는 `0x44`바이트뿐이지만 4 KiB로 잡는다.
> BAR가 호스트 페이지 크기보다 작으면 VFIO에서 사용자 공간 mmap이
> 제한된다. §1.2의 M3 VFIO 계획을 지금 막지 않기 위한 선택이다.
>
> 다만 64 KiB 페이지 커널(aarch64에서 가능)에서는 4 KiB도 여전히
> sub-page다. 완전한 해결은 아니며, M3에서 재검토한다.

**NACC-REQ-052** `[SW]` 드라이버는 BAR0을 **기본 I/O 속성**으로
매핑해야 한다(MUST). write-combining 등 비기본 속성으로 매핑해서는
안 된다(MUST NOT).

> 근거: §4.3의 순서 보장은 기본 속성으로 매핑된 `__iomem` 포인터에만
> 적용된다. 비기본 속성의 순서 성질은 아키텍처 의존이며, 그 경우
> §4.3의 요구사항이 전부 무효가 된다.
>
> 이 요구사항이 없으면 §4.3의 "배리어가 필요 없다"가 성립하는
> 전제 조건이 문서 어디에도 없게 된다.

### 2.3 인터럽트

| 방식  | 벡터 수 | 지원 여부           |
| ----- | ------- | ------------------- |
| MSI   | 1       | 지원                |
| MSI-X | —       | 미지원 (M1 범위 밖) |
| INTx  | —       | 미지원              |

**NACC-REQ-004** `[HW]` 디바이스는 MSI를 지원하며 벡터는 1개다.
INTx와 MSI-X는 지원하지 않는다.

**NACC-REQ-005** `[HW]` 디바이스가 인터럽트를 전달하려면 PCI Command
레지스터의 Bus Master Enable 비트가 1이어야 한다.

**NACC-REQ-006** `[SW]` 드라이버는 인터럽트를 요청하기 전에
`pci_set_master()`를 호출해야 한다(MUST).

> 근거: MSI는 호스트 메모리로 향하는 posted write이므로 DMA와 동일한
> upstream 경로를 쓴다. BME가 0이면 그 경로가 차단된다.
>
> M0 검증 기록: 이 호출이 누락되면 MSI 할당은 성공하지만 인터럽트가
> 전달되지 않으며, `/proc/interrupts` 카운트가 증가하지 않는다.
> 오류 표시가 없으므로 조용히 실패한다. `lspci -v`의 Flags 줄에
> `bus master`가 없는 것이 진단 신호다.

### 2.4 리비전 정책

**NACC-REQ-007** `[SW]` 드라이버는 Revision ID가 자신이 아는 값보다 크면
경고를 남기고 계속 진행해야 한다(SHOULD). 작으면 바인딩을 거부해야 한다(MUST).

> 근거: 상위 리비전은 하위 호환을 유지한다고 전제한다. 하위 리비전은
> 이 문서가 정의한 레지스터가 없을 수 있으므로 안전하지 않다.

**NACC-REQ-008** `[HW]` 리비전 2 이상은 아래를 지킨다(MUST).

- 리비전 1에 정의된 레지스터의 오프셋과 폭을 바꾸지 않는다
- 리비전 1에 정의된 필드의 의미를 바꾸지 않는다
- 새 기능은 예약 필드 또는 `0x0044` 이후의 새 오프셋에만 추가한다

> 근거: §4.4의 예약 필드 보존 정책과 짝을 이룬다. 이 약속이 없으면
> 예약 비트를 보존하는 것이 무의미하다.

## §3. 디바이스 상태 머신

### 3.1 상태 목록

```
                    ┌─────────┐
                    │  RESET  │  ← 전원 인가 / PCI 리셋 직후
                    │  (0)    │
                    └────┬────┘
                         │ T1: RING_BASE_HI 쓰기
                    ┌────▼────┐
              ┌────►│  INIT   │  ← 링 설정 중. ENABLE=0
              │     │  (1)    │
              │     └────┬────┘
              │          │ T2: ENABLE←1 (설정 유효)
              │     ┌────▼────┐  T4: doorbell   ┌─────────┐
              │     │  READY  ├────────────────►│  BUSY   │
              │     │  (2)    │◄────────────────┤  (3)    │
              │     └──┬───┬──┘  T6: 전부 완료  └──┬───┬──┘
              │        │   │                       │   │
              │   T5   │   │                T7/T12 │   │
              │        ▼   │                       ▼   │
              │   ┌─────────┐                          │
              │   │  ERROR  │◄─────────────────────────┘
              │   │  (5)    │
              │   └────┬────┘
              │        │
              │        │ T8: ENABLE←0
              │   ┌────▼────┐
              └───┤ HALTING │  ← DMA 정지 대기. 유한 시간
             T9   │  (4)    │
                  └─────────┘
                       ▲
                       │ T8: ENABLE←0 (READY / BUSY 에서도)
```

**상태 인코딩** (`STATUS.STATE`, §5.3 참조)

| 값      | 상태      | 의미                          |
| ------- | --------- | ----------------------------- |
| `0`     | `RESET`   | 링 미설정                     |
| `1`     | `INIT`    | 링 설정됨, 비활성             |
| `2`     | `READY`   | 활성, 진행 중 명령 없음       |
| `3`     | `BUSY`    | 활성, 진행 중 명령 있음       |
| `4`     | `HALTING` | 정지 진행 중. DMA 미완료 가능 |
| `5`     | `ERROR`   | 오류 정지. `ERR_CODE` 유효    |
| `6`–`7` | 예약      | M2 펌웨어 상태용              |

**설계 판단 기록**

- `INIT`과 `READY`를 분리한다. 분리하지 않으면 링 물리 주소가 유효하기
  전에 `ENABLE`이 1이 될 수 있고, 디바이스가 임의 주소를 DMA한다.
  두 상태를 나누면 "설정 완료"라는 관측 가능한 경계가 생긴다.
- `BUSY`는 카운터가 아니라 상태다. `BUSY`에서만 금지되는 동작
  (`RING_SIZE` 변경 등)이 있고, `STATUS`만 읽어서 그 사실을 알 수 있어야
  하기 때문이다.
- `HALTING`을 신설한다. `ENABLE ← 0` 직후에도 이미 발행된 PCIe 트랜잭션이
  회수 중일 수 있다. 이 구간을 상태로 만들지 않으면 드라이버는 DMA 버퍼를
  언제 해제해도 안전한지 알 수 없다.

### 3.2 전이표

각 행이 하나의 전이다. 표에 없는 (상태, 트리거) 조합은 §3.3의 금지 동작
항목과 아래 "전이표에 없는 조합" 표가 정의한다. **빈칸을 남기지 않는다.**

| ID  | 현재 상태              | 트리거                                    | 다음 상태 | 하드웨어 부수효과                                                                                        |
| --- | ---------------------- | ----------------------------------------- | --------- | -------------------------------------------------------------------------------------------------------- |
| T1  | `RESET`                | `RING_BASE_HI` 쓰기                       | `INIT`    | `{HI,LO}` 쌍을 래치. 링 메모리는 읽지 않음                                                               |
| T2  | `INIT`                 | `CTRL.ENABLE ← 1`, 설정 유효 (§3.5)       | `READY`   | `RING_CONS ← 0`, `RING_PROD ← 0`, `ERR_CODE ← 0`. 링 메모리는 읽지 않음                                  |
| T3  | `INIT`                 | `CTRL.ENABLE ← 1`, 설정 무효 (§3.5)       | `ERROR`   | `ERR_CODE ← BAD_CONFIG`. `IRQ_STATUS.CMD_ERR ← 1`. 링 설정값은 보존                                      |
| T4  | `READY`                | `RING_PROD` 쓰기, 값 유효, `prod ≠ cons`  | `BUSY`    | 디스크립터 페치 시작                                                                                     |
| T5  | `READY`                | `RING_PROD` 쓰기, 값 무효 (`≥ RING_SIZE`) | `ERROR`   | `ERR_CODE ← BAD_PROD`. `IRQ_STATUS.CMD_ERR ← 1`. `RING_CONS` 불변                                        |
| T6  | `BUSY`                 | `RING_CONS == RING_PROD` 도달             | `READY`   | `IRQ_STATUS.CMD_DONE ← 1`                                                                                |
| T7  | `BUSY`                 | 디스크립터 검증 실패 또는 DMA 실패 (§8.1) | `ERROR`   | 실행 중단. `ERR_CODE ← 원인`. `RING_CONS`는 실패한 디스크립터를 가리킨 채 고정. `IRQ_STATUS.CMD_ERR ← 1` |
| T8  | `READY` `BUSY` `ERROR` | `CTRL.ENABLE ← 0`                         | `HALTING` | 새 디스크립터 페치 중단. 진행 중 명령은 완료 보고 없이 폐기. §3.4 참조                                   |
| T9  | `HALTING`              | 미처리 PCIe 트랜잭션 회수 완료            | `INIT`    | `ERR_CODE` 보존. `IRQ_STATUS` 보존. 링 설정값 보존                                                       |
| T10 | `RESET`                | `CTRL.ENABLE ← 1`                         | `ERROR`   | `ERR_CODE ← BAD_CONFIG`. `IRQ_STATUS.CMD_ERR ← 1`                                                        |
| T11 | `BUSY`                 | `RING_PROD` 쓰기, 값 유효                 | `BUSY`    | 새 디스크립터를 대기열에 추가. 상태 변화 없음                                                            |
| T12 | `BUSY`                 | `RING_PROD` 쓰기, 값 무효 (`≥ RING_SIZE`) | `ERROR`   | 실행 중단. `ERR_CODE ← BAD_PROD`. `RING_CONS`는 현재 값으로 고정. `IRQ_STATUS.CMD_ERR ← 1`               |

**전이표에 없는 조합의 처리**

| 상황                                          | 동작                                 |
| --------------------------------------------- | ------------------------------------ |
| `READY`에서 `RING_PROD` 쓰기, `prod == cons`  | 무시. 상태 변화 없음. 오류 아님      |
| `INIT` `HALTING` `ERROR`에서 `RING_PROD` 쓰기 | 쓰기 무시. 상태 변화 없음. 오류 아님 |
| `RESET`에서 `RING_PROD` 쓰기                  | 쓰기 무시. 상태 변화 없음. 오류 아님 |
| 이미 `ENABLE = 1`인 상태에서 `ENABLE ← 1`     | 무시. 상태 변화 없음                 |
| `RESET` `INIT` `HALTING`에서 `ENABLE ← 0`     | 무시. 상태 변화 없음                 |
| 임의 상태에서 예약 비트만 변경하는 쓰기       | §4.4. 상태 변화 없음                 |

> **T12를 신설한 이유 (v0.3):**
> v0.2는 `BUSY`에서 `RING_PROD`에 무효값을 쓴 경우를 T7에 얹으려 했다.
> 그러나 T7의 정의는 "디스크립터 검증 실패 또는 DMA 실패"이므로
> 인덱스 오류가 들어가지 않는다. 전이표에 없는 조합이 하나 있었던
> 셈이고, 이는 §3.2의 "빈칸을 남기지 않는다" 위반이다.

> **T2의 "링 메모리는 읽지 않음"이 왜 중요한가:**
> 이걸 명시하지 않으면 드라이버가 `ENABLE`을 켜기 전에 링 전체를 0으로
> 초기화해야 하는지 알 수 없다. 하드웨어가 안 읽는다고 못박으면
> 드라이버는 첫 doorbell 직전까지 링을 건드리지 않아도 된다.

> **T7의 "`RING_CONS`가 실패한 디스크립터를 가리킨 채 고정"이 §9 Q2의 답이다.**
> 이 한 줄이 없으면 드라이버는 어느 명령이 실패했는지 알 수 없고,
> 오류가 곧 전체 링 재생성이 된다.

> **`ERROR` 탈출은 T8 하나뿐이다.** > `ENABLE ← 0` → `HALTING` → `INIT` → `ENABLE ← 1` 경로가 이미 완전한
> 복구 시퀀스이므로, 별도의 리셋 비트를 두면 같은 일을 하는 메커니즘이
> 둘이 된다. 그 결과 `CTRL[1]`이 비었고, 예약 필드로 남겨 두었다.

**NACC-REQ-054** `[HW]` `ERROR`로 전이할 때 디바이스는
`ERR_CODE`와 `STATUS.STATE`를 먼저 갱신하고, **그 다음에**
`IRQ_STATUS.CMD_ERR`을 세운다(MUST).

> 근거: 인터럽트 핸들러는 `CMD_ERR`을 보고 `ERR_CODE`와 `STATUS`를
> 읽는다. 순서가 반대이면 핸들러가 옛 `ERR_CODE`를 읽는 경쟁이 난다.
> 이 순서를 명시하지 않으면 재현 빈도가 낮은 오진단 버그가 된다.
>
> `RING_CONS` 고정도 같은 순서에 포함된다 — `CMD_ERR`을 세우는
> 시점에 `RING_CONS`는 이미 최종값이어야 한다.

### 3.3 상태별 상세

각 상태마다 아래 항목을 빠짐없이 작성한다.
**항목 3(위반 시 하드웨어 동작)을 비워두면 반드시 버그가 난다.**

항목 3은 **관측 가능한 하드웨어 동작만** 기술한다. 드라이버가 그 상황에서
무엇을 로깅하는지는 이 문서의 관심사가 아니다.

---

#### `RESET` (STATE = 0)

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `RING_PROD` 쓰기 (doorbell)
   - `CTRL.ENABLE ← 1` — 링 물리 주소가 미설정이므로 디바이스가
     유효하지 않은 주소를 DMA할 수 있다

3. **위반 시 하드웨어 동작**

   - `RING_PROD` 쓰기: 쓰기 무시. 레지스터 값 불변. 상태 변화 없음.
     `ERR_CODE` 불변. 인터럽트 없음
   - `CTRL.ENABLE ← 1`: **T10**. `ERROR`로 전이하고
     `ERR_CODE ← BAD_CONFIG`, `IRQ_STATUS.CMD_ERR ← 1`

4. **체류 시간 제약**
   없음. 무한정 머물 수 있다.

---

#### `INIT` (STATE = 1)

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `RING_PROD` 쓰기 (doorbell)
   - §3.5의 설정 유효성을 만족하지 않는 상태에서 `CTRL.ENABLE ← 1`

3. **위반 시 하드웨어 동작**

   - `RING_PROD` 쓰기: 쓰기 무시. 레지스터 값 불변. 상태 변화 없음.
     `ERR_CODE` 불변. 인터럽트 없음
   - 무효 설정으로 `ENABLE ← 1`: **T3**. `ERROR`로 전이,
     `ERR_CODE ← BAD_CONFIG`, `IRQ_STATUS.CMD_ERR ← 1`.
     **`RING_BASE_*`와 `RING_SIZE`는 지워지지 않는다.**

   > 값을 지워버리면 드라이버가 무엇이 잘못됐는지 읽어볼 수 없다.
   > 값을 남기면 `RING_SIZE`를 읽어서 원인을 확인할 수 있다.

4. **체류 시간 제약**
   없음. 무한정 머물 수 있다.

---

#### `READY` (STATE = 2)

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `RING_BASE_LO/HI`, `RING_SIZE` 쓰기
   - `RING_PROD`에 `RING_SIZE` 이상의 값 쓰기
   - 링이 가득 찬 상태(§6.3)에서 `RING_PROD` 전진

3. **위반 시 하드웨어 동작**

   - `RING_BASE_*` / `RING_SIZE` 쓰기: 쓰기 무시. 레지스터 값 불변.
     상태 변화 없음. 인터럽트 없음
   - 범위를 벗어난 `RING_PROD` 쓰기: **T5**. `ERROR`로 전이,
     `ERR_CODE ← BAD_PROD`
   - 가득 찬 링에 전진: 하드웨어는 이를 검출하지 않는다.
     `prod`가 `cons`를 추월하면 디바이스는 아직 처리하지 않은
     디스크립터를 덮어쓴 것으로 간주하고 그대로 실행한다. 동작 미정의.

   > 링 full 검출을 하드웨어에 넣지 않은 이유: `prod`와 `cons`만으로는
   > "한 바퀴 돈 것"과 "비어 있는 것"을 구분할 수 없다. §6.3에서
   > 한 슬롯을 비워두는 규약(`[SW]`)으로 해결한다.

4. **체류 시간 제약**
   없음. 무한정 머물 수 있다.

---

#### `BUSY` (STATE = 3)

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `RING_BASE_LO/HI`, `RING_SIZE` 쓰기
   - `RING_PROD`에 `RING_SIZE` 이상의 값 쓰기
   - `RING_CONS`가 아직 지나가지 않은 슬롯의 디스크립터 수정

3. **위반 시 하드웨어 동작**

   - `RING_BASE_*` / `RING_SIZE` 쓰기: 쓰기 무시. 레지스터 값 불변.
     상태 변화 없음. 인터럽트 없음
   - 범위를 벗어난 `RING_PROD` 쓰기: **T12**. `ERROR`로 전이,
     `ERR_CODE ← BAD_PROD`. 진행 중이던 명령은 중단된다
   - 진행 중 슬롯 수정: 하드웨어는 검출하지 않는다. 디바이스가 어느
     시점에 그 슬롯을 읽는지는 미정의이므로 결과도 미정의

   > `CTRL.ENABLE ← 0`은 `BUSY`에서 **금지 동작이 아니다.** T8이며,
   > 이것이 진행 중 명령을 중단시키는 유일한 정상 수단이다.

4. **체류 시간 제약**
   **하드웨어는 상한을 보장하지 않는다.** 명령 처리 시간은 호스트 메모리
   접근 지연에 의존하며, 디바이스는 그 지연을 제어할 수 없다.

   상한은 소프트웨어가 소유한다. NACC-REQ-096 참조.

**NACC-REQ-096** `[SW]` 드라이버는 `BUSY` 체류에 대한 자체 타임아웃을
가져야 한다(MUST). 타임아웃 시 `CTRL.ENABLE ← 0`으로 T8을 유발하고
§3.4의 정지 시퀀스를 수행해야 한다.

> 근거: 하드웨어가 상한을 보장하지 않으므로 상한을 아는 쪽이 소유해야
> 한다. 드라이버는 요청한 전송 크기를 알고 있고(NACC-REQ-035가 상한을
> 1 MiB로 고정한다) 링 깊이도 알고 있으므로 합리적인 상한을 계산할 수 있다.

---

#### `HALTING` (STATE = 4)

`ENABLE ← 0` 이후, 디바이스가 이미 발행한 PCIe 트랜잭션이 모두 회수될
때까지의 과도 상태다.

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `CTRL.ENABLE ← 1` 쓰기
   - `RING_PROD` 쓰기
   - **링 메모리 또는 `MEMCPY` 대상 버퍼의 DMA 매핑 해제 / 메모리 해제**

3. **위반 시 하드웨어 동작**

   - `CTRL.ENABLE ← 1`: 쓰기 무시. `CTRL` 값 불변. 상태 변화 없음
   - `RING_PROD` 쓰기: 쓰기 무시. 상태 변화 없음
   - 버퍼 해제: 하드웨어는 검출할 수 없다. 회수되지 않은 읽기 완료가
     해제된 메모리에 도달하면 결과는 미정의다

4. **체류 시간 제약**
   **유한하다.** 디바이스는 유한 시간 내에 T9를 완료한다(MUST).
   구체적 상한은 구현 정의다.

5. **탈출 경로**
   T9 (`INIT`). 자동이며 드라이버 개입 없음.

**NACC-REQ-090** `[HW]` `HALTING` 진입 시점 이후 디바이스는 새로운
메모리 읽기/쓰기 요청을 발행하지 않는다(MUST).

**NACC-REQ-091** `[HW]` T9는 디바이스가 발행한 모든 메모리 요청이
회수된 뒤에만 일어난다(MUST). 즉 `STATUS.STATE ≠ HALTING`을 관측한
시점에 이 디바이스로 인한 미처리 DMA는 존재하지 않는다.

> 이 두 요구사항이 없으면 드라이버는 DMA 버퍼를 언제 해제해도 안전한지
> 알 수 없다.

**NACC-REQ-092** `[SW]` 드라이버는 `CTRL.ENABLE ← 0` 이후
`STATUS.STATE`를 폴링하여 `HALTING`을 벗어난 것을 확인한 뒤에만
DMA 버퍼를 해제해야 한다(MUST). 폴링에는 상한 시간을 두어야 한다(MUST).

> 근거: `readl_poll_timeout()`을 그대로 쓸 수 있는 형태다.
> 상한 초과는 하드웨어 고장으로 간주하며, 그 경우 버퍼를 해제하지
> 않고 누수시키는 편이 안전하다.

---

#### `ERROR` (STATE = 5)

1. **접근 가능한 레지스터** — §5.2 행렬 참조

2. **드라이버가 하면 안 되는 것**

   - `RING_PROD` 쓰기
   - `RING_BASE_LO/HI`, `RING_SIZE` 쓰기

3. **위반 시 하드웨어 동작**

   - `RING_PROD` 쓰기: 쓰기 무시. 상태 변화 없음. `ERR_CODE` 불변
   - `RING_BASE_*` / `RING_SIZE` 쓰기: 쓰기 무시. 값 불변

4. **체류 시간 제약**
   없음. 무한정 머물 수 있다.

5. **탈출 경로**
   T8 (`ENABLE ← 0` → `HALTING`) 하나뿐이다.
   이후 `INIT`에서 `ENABLE ← 1`로 재활성화한다.

**NACC-REQ-093** `[HW]` `ERROR` 상태에서 `ERR_CODE`와 `RING_CONS`는
고정된다. T2(`ENABLE ← 1`)가 일어날 때까지 값이 유지된다(MUST).

> 근거: 진단 정보는 복구 시퀀스 도중에 사라지면 쓸모가 없다.
> `HALTING`과 `INIT`을 거치는 동안에도 보존해야 드라이버가 여유 있게
> 읽을 수 있다.

### 3.4 정지(quiesce) 시퀀스

`CTRL.ENABLE ← 0`의 의미론을 한곳에 모은다. M3의 FLR은 이 절을 승계한다.

**NACC-REQ-094** `[HW]` `CTRL.ENABLE ← 0` 시 진행 중인 명령은
**완료를 기다리지 않고 폐기된다**(MUST). 폐기된 명령에 대해서는
완료 인터럽트가 발생하지 않으며, `RING_CONS`도 전진하지 않는다.

> 근거(drain 방식을 기각한 이유): 명령 완료까지 대기하는 방식은
> 완료 시간의 상한을 하드웨어가 보장할 수 있을 때만 성립한다.
> §3.3 `BUSY` 항목 4에 따라 그 보장이 없으므로, drain을 택하면
> 결국 타임아웃 후 강제 중단 경로가 별도로 필요해진다.
> 메커니즘이 하나면 검증할 것도 하나다.

**NACC-REQ-095** `[HW]` `HALTING` 진입 시점에 `RING_CONS`가 가리키는
값은 "폐기 경계"다. `[0, cons)` 범위의 명령은 완료되었고,
`[cons, prod)` 범위의 명령은 폐기되었다.

> 이 한 줄로 드라이버는 어느 버퍼가 실제로 전송되었고 어느 것이
> 취소되었는지 알 수 있다. 없으면 전부 실패로 간주해야 한다.

**표준 정지 시퀀스 (드라이버 관점)**

1. `IRQ_MASK`의 모든 비트를 1로 써서 인터럽트 전달을 차단한다
2. `CTRL.ENABLE ← 0`
3. `STATUS.STATE ≠ HALTING`이 될 때까지 폴링 (상한 있음)
4. `RING_CONS`를 읽어 폐기 경계를 확인한다
5. `IRQ_STATUS`를 읽고 **읽은 값을 그대로 되써서** 클리어한다
6. 미완료 버퍼를 DMA 언매핑하고 상위 계층에 취소를 보고한다
7. 링 메모리를 해제한다

**NACC-REQ-056** `[SW]` 드라이버는 `IRQ_MASK`를 해제하기 전에
`IRQ_STATUS`를 클리어해야 한다(MUST).

> 근거: NACC-REQ-063에 따라 마스킹 중에도 `IRQ_STATUS` 비트는
> 세워진다. NACC-REQ-065에 따라 마스크를 해제하는 순간
> `(IRQ_STATUS & ~IRQ_MASK)`가 0에서 0이 아닌 값이 되면 MSI가 발행된다.
> 클리어하지 않고 해제하면 정지 이전의 이벤트가 재초기화 직후
> 유령 인터럽트로 되살아난다.
>
> 위 시퀀스의 1번(마스킹)과 5번(클리어)이 짝이다. 1번만 하고
> 5번을 빠뜨리는 것이 흔한 실수다.

> 1번을 먼저 하는 이유: 3번 폴링 중에 이전 명령의 완료 인터럽트가
> 도착할 수 있다. 마스킹하지 않으면 해제 중인 자료구조를 인터럽트
> 핸들러가 건드린다.

### 3.5 설정 유효성 판정

T2/T3의 분기 기준이다. `CTRL.ENABLE ← 1` 시점에 디바이스가 검사한다.

**NACC-REQ-097** `[HW]` 아래를 **모두** 만족하면 설정이 유효하다.
하나라도 어기면 T3(또는 `RESET`에서는 T10)이 일어난다.

| 항목        | 조건                                        |
| ----------- | ------------------------------------------- |
| 현재 상태   | `INIT`이어야 한다 (`RESET`이면 무조건 무효) |
| `RING_SIZE` | 2의 거듭제곱, `2 ≤ RING_SIZE ≤ 128`         |
| `RING_BASE` | 하위 5비트가 0 (32바이트 정렬, §6.2)        |
| `RING_BASE` | `0`이 아니어야 한다                         |

> 검사를 `ENABLE ← 1` 한 시점에 몰아서 하는 이유: 개별 레지스터 쓰기
> 시점마다 검사하면 "LO는 썼고 HI는 아직"인 중간 상태에서 오탐이 난다.

**NACC-REQ-098** `[HW]` 설정 유효성 판정에 사용하는 `RING_BASE` 값은
NACC-REQ-011의 **래치된 값**이다. 섀도 레지스터의 `LO` 값이 아니다.

> 래치 규칙을 §4.1에만 적어 두면 유효성 판정 구현에서 놓치기 쉽다.
> 두 곳에 적는다.

## §4. 전역 접근 규칙

> 이 절이 빠진 데이터시트는 반드시 이식 버그를 만든다.

### 4.1 접근 폭

**NACC-REQ-010** `[HW]` 모든 레지스터는 32비트 정렬 접근만 허용한다(MUST).
8/16/64비트 접근의 동작은 미정의다.

**NACC-REQ-011** `[HW]` `RING_BASE_LO`(`0x0020`)와 `RING_BASE_HI`(`0x0024`)는
섀도-래치 방식으로 동작한다.

- `RING_BASE_LO` 쓰기는 섀도 레지스터에만 반영된다. 디바이스 내부의
  유효 링 주소는 바뀌지 않는다.
- `RING_BASE_HI` 쓰기 시점에 `{HI, LO}` 64비트 값이 함께 래치된다.
  이 시점에 `RESET` 상태였다면 T1이 일어난다.
- 두 레지스터를 읽으면 각각 마지막으로 쓴 값이 반환된다.

**NACC-REQ-012** `[SW]` 드라이버는 링 베이스 주소를 설정할 때
`RING_BASE_LO`를 먼저, `RING_BASE_HI`를 나중에 써야 한다(MUST).
상위 32비트만 바꾸고 싶더라도 두 레지스터를 모두 써야 한다(MUST).

> 근거: NACC-REQ-010이 32비트 접근만 허용하므로 64비트 값을 원자적으로
> 쓸 방법이 없다. 래치 시점을 `HI` 쓰기로 고정하면 순서 규칙 하나로
> 원자성을 대체할 수 있다.
>
> 두 쓰기 사이에 배리어는 필요 없다 — NACC-REQ-017이 순서를 보장한다.

### 4.2 엔디안

**NACC-REQ-013** `[HW]` MMIO 레지스터는 리틀엔디안이다.
드라이버는 `readl()` / `writel()`을 사용해야 한다(MUST).

**NACC-REQ-014** `[HW]` 호스트 메모리의 디스크립터 필드도 리틀엔디안이다.
드라이버는 `cpu_to_le32()` / `cpu_to_le64()` 계열 변환을 사용해야 한다(MUST).

> 두 문장을 분리해서 쓴다. MMIO와 디스크립터의 엔디안이 다른 하드웨어가
> 실제로 존재한다.

### 4.3 순서 및 배리어

이 절의 `[SW]` 요구사항은 모두 **BAR0이 기본 I/O 속성으로 매핑되어
있음**(NACC-REQ-052)을 전제한다.

**NACC-REQ-015** `[HW]` 디바이스는 디스크립터 링 메모리의 내용과
doorbell 레지스터 쓰기 사이의 순서를 보장하지 않는다. 디바이스가
doorbell 쓰기를 관측한 시점에 해당 디스크립터가 메모리에 보이지 않으면
디바이스는 옛 내용을 읽는다.

**NACC-REQ-016** `[SW]` 드라이버는 디스크립터를 쓴 뒤 `writel()`로
doorbell(`RING_PROD`)을 써야 한다(MUST). 그 사이에 별도의 배리어를
넣을 필요는 없다(MAY 생략).

> 근거: 리눅스의 `writeX()`는 같은 스레드가 앞서 발행한 메모리 쓰기가
> 완료되기를 먼저 기다린다. 커널 문서가 드는 예시가 바로 이 상황이다 —
> `dma_alloc_coherent()`로 잡은 아웃바운드 버퍼에 CPU가 쓴 내용이,
> MMIO 제어 레지스터를 써서 전송을 트리거할 때 DMA 엔진에 보인다는 것.
>
> 즉 NACC-REQ-015가 요구하는 가시성은 `writel()` 자체가 제공한다.
> v0.2 초안의 `dma_wmb()`는 중복이었다.

**NACC-REQ-017** `[HW]` 서로 다른 MMIO 레지스터에 대한 연속 접근은
프로그램 순서대로 디바이스에 도달한다. 드라이버는 MMIO 접근 **사이에**
배리어를 넣을 필요가 없다.

> 근거: 같은 peripheral에 대한 `readX()`/`writeX()`는 서로 순서가
> 보장되며, 같은 CPU 스레드가 발행한 MMIO 레지스터 접근은 프로그램
> 순서로 도착한다. 이 보장은 relaxed 변형에서도 유지된다.
>
> v0.1의 "순서대로 동작하지 않는다"는 틀렸다. §9 Q5에서 확정.

**NACC-REQ-018** `[SW]` 드라이버는 `readl()`로 `RING_CONS`를 읽어
슬롯 완료를 확인한 뒤, 해당 디스크립터의 `status` 필드와 대상 버퍼를
별도의 배리어 없이 읽을 수 있다(MAY).

> 근거: `readX()`는 같은 스레드의 후속 메모리 읽기가 시작되기 전에
> 완료된다. 커널 문서의 예시가 이 상황이다 — DMA 엔진의 MMIO 상태
> 레지스터를 읽어 전송 완료를 확인한 뒤 인바운드 버퍼를 읽을 때
> 오래된 데이터를 보지 않는다는 것.
>
> 이 보장은 하드웨어 측 NACC-REQ-043과 짝을 이룰 때만 충분조건이 된다.
> 한쪽만 있으면 반쪽이다.

**NACC-REQ-053** `[SW]` 드라이버는 doorbell 쓰기와 `RING_CONS` 읽기에
`writel_relaxed()` / `readl_relaxed()`를 사용해서는 안 된다(MUST NOT).

> 근거: relaxed 변형은 NACC-REQ-017이 근거로 든 "같은 peripheral 접근
> 간 순서"는 유지하지만, NACC-REQ-016·018이 근거로 든 "메모리 접근과의
> 순서"는 보장하지 않는다. 두 경로가 다른 보장에 의존한다는 점을
> 명시해 둔다.
>
> M1에서 relaxed를 쓸 이유도 없다. 제출 경로에 doorbell 한 번,
> 완료 경로에 `RING_CONS` 한 번이므로 배리어 비용이 병목이 될 수 없다.
> relaxed는 링당 수십 번씩 MMIO를 치는 경로에서 의미가 있다.
>
> `STATUS` 폴링처럼 메모리 접근과 엮이지 않는 경로에서는 relaxed를
> 써도 무방하지만, 일관성을 위해 M1에서는 전부 non-relaxed로 통일한다.

### 4.4 예약 필드 정책

**NACC-REQ-019** `[HW]` RW 레지스터의 예약(`RSVD`) 필드에 대한 디바이스 동작:

- 읽기: 마지막으로 쓴 값을 그대로 반환한다. 리셋값은 0이다
- 쓰기: 값을 저장하되 어떤 동작도 유발하지 않는다
- 예약 필드에 대한 쓰기는 오류가 아니다. 상태 전이도 인터럽트도 없다

RO 레지스터의 예약 필드는 예외다. 항상 0을 반환하며, 쓰기는
레지스터 전체가 무시된다.

**NACC-REQ-020** `[SW]` 드라이버는 레지스터를 쓸 때 read-modify-write를
사용하여 예약 비트의 값을 **해석하지 않고 그대로 되써야** 한다(MUST).

```c
/* NACC-REQ-020 */
val = readl(base + NACC_REG_CTRL);
val |= NACC_CTRL_ENABLE;
writel(val, base + NACC_REG_CTRL);
```

> 근거: 미래 리비전에서 예약 비트를 사용하게 되더라도 구버전 드라이버가
> 해당 비트를 0으로 밀어버리지 않는다. NACC-REQ-008의 "추가만 허용"
> 정책과 짝을 이룬다.
>
> 대안이었던 `RAZ/WI`(읽으면 0, 쓰면 무시)는 하드웨어 구현이 더 단순하지만
> 확장 시 호환성을 잃는다. 기각.

### 4.5 정렬 및 미매핑 영역

**NACC-REQ-021** `[HW]` BAR0 내에서 레지스터가 정의되지 않은 오프셋에 대한
접근:

- 읽기: `0x00000000`을 반환한다
- 쓰기: 무시된다. 상태 변화 없음. `ERR_CODE` 불변. 인터럽트 없음

> 쓰기 쪽: PCIe의 메모리 쓰기는 posted write이므로 완료 응답 자체가
> 없다. 반환할 값이 없고, 드라이버의 `writel()`도 값을 받지 않는다.
> 하드웨어가 "에러를 반환"하는 것은 물리적으로 불가능하다.
>
> 읽기 쪽: `0xFFFFFFFF`는 디바이스가 응답하지 않을 때 루트 컴플렉스가
> 합성하는 값이다. NACC-REQ-024가 그 값을 링크 다운 신호로 쓰므로,
> 정의되지 않은 오프셋이 같은 값을 반환하면 두 상황을 구분할 수 없다.
> `0`을 반환하도록 정한다.

### 5.2 접근 가능 행렬

**이 표가 정본이다.** §3.3과 §5.3은 이 표를 참조한다.

| 표기  | 의미                                                           |
| ----- | -------------------------------------------------------------- |
| `RW`  | 읽기/쓰기 모두 허용                                            |
| `R`   | 읽기만 허용. 쓰기는 무시되며 상태 변화도 인터럽트도 없다       |
| `R!`  | 읽기만 허용. **쓰기가 상태 전이를 유발한다** — 각주 참조       |
| `RW!` | 읽기/쓰기 허용. **특정 값이 상태 전이를 유발한다** — 각주 참조 |

| 레지스터       | `RESET` | `INIT` | `READY` | `BUSY` | `HALTING` | `ERROR` |
| -------------- | ------- | ------ | ------- | ------ | --------- | ------- |
| `ID`           | R       | R      | R       | R      | R         | R       |
| `CTRL`         | R!¹     | RW     | RW      | RW     | R         | RW      |
| `STATUS`       | R       | R      | R       | R      | R         | R       |
| `IRQ_STATUS`   | RW      | RW     | RW      | RW     | RW        | RW      |
| `IRQ_MASK`     | RW      | RW     | RW      | RW     | RW        | RW      |
| `RING_BASE_LO` | RW      | RW     | R       | R      | R         | R       |
| `RING_BASE_HI` | RW!²    | RW     | R       | R      | R         | R       |
| `RING_SIZE`    | RW      | RW     | R       | R      | R         | R       |
| `RING_PROD`    | R       | R      | RW!³    | RW!³   | R         | R       |
| `RING_CONS`    | R       | R      | R       | R      | R         | R       |
| `ERR_CODE`     | R       | R      | R       | R      | R         | R       |

**각주**

1. `RESET`에서 `CTRL.ENABLE ← 1`은 무시되지 않는다. **T10**을 유발하여
   `ERROR`로 간다. `ENABLE ← 0`과 예약 비트만 바꾸는 쓰기는 무시된다.
2. `RESET`에서 `RING_BASE_HI` 쓰기는 **T1**을 유발한다(NACC-REQ-011).
3. `READY`/`BUSY`에서 `RING_PROD` 쓰기는 값에 따라
   **T4/T5/T11/T12** 중 하나를 유발한다(NACC-REQ-074).

> `INIT`에서 `CTRL`이 `RW`인 것에 주의. T2는 `INIT`에서 `ENABLE ← 1`을
> 쓰는 전이이므로 여기서 쓰기가 막히면 `READY`에 도달할 방법이 없다.
>
> `HALTING`에서 `CTRL`이 `R`인 이유: `ENABLE ← 1`은 무시되고,
> `ENABLE ← 0`은 이미 0이므로 의미가 없다.

### 5.3 레지스터 상세

---

#### `ID` — 디바이스 식별 (오프셋 `0x0000`, 32bit, RO)

| 비트      | 이름    | 속성 | 리셋값   | 설명            |
| --------- | ------- | ---- | -------- | --------------- |
| `[31:16]` | `MAGIC` | RO   | `0x4E41` | 고정 매직값     |
| `[15:8]`  | `RSVD`  | RSVD | `0`      | §4.4 (RO 예외)  |
| `[7:0]`   | `REV`   | RO   | `0x01`   | 하드웨어 리비전 |

> `MAGIC`은 `'N'`(`0x4E`), `'A'`(`0x41`)의 ASCII다. 16비트 필드이므로
> 두 글자만 담는다.

**NACC-REQ-023** `[HW]` `ID`는 모든 상태에서 같은 값을 반환한다(MUST).
`RESET` 상태에서도 유효하다.

**NACC-REQ-024** `[SW]` 드라이버는 probe 시 `ID.MAGIC`을 읽어 기대값과
비교해야 한다(MUST). 불일치 시 바인딩을 거부해야 한다.

> 근거: BAR 매핑이 잘못되었거나 디바이스가 응답하지 않는 경우를
> probe 단계에서 걸러낸다. 전체 값이 `0xFFFFFFFF`이면 대개 링크 다운이다.
> §4.5에 따라 정의되지 않은 오프셋은 `0`을 반환하므로, `0xFFFFFFFF`는
> 링크 다운 전용 신호로 해석할 수 있다.

---

#### `CTRL` — 전역 제어 (오프셋 `0x0008`, 32bit, RW)

| 비트     | 이름     | 속성 | 리셋값 | 설명                    |
| -------- | -------- | ---- | ------ | ----------------------- |
| `[31:1]` | `RSVD`   | RSVD | `0`    | §4.4                    |
| `[0]`    | `ENABLE` | RW   | `0`    | 1: 활성화, 0: 정지 요청 |

**NACC-REQ-025** `[HW]` `INIT`에서 `ENABLE ← 1`은 §3.5의 설정 유효성에
따라 T2 또는 T3을 유발한다.

**NACC-REQ-026** `[HW]` `RESET`에서 `ENABLE ← 1`은 T10을 유발한다.

**NACC-REQ-027** `[HW]` `READY`/`BUSY`/`ERROR`에서 `ENABLE ← 0`은 T8을
유발한다. 상세 의미론은 §3.4 참조.

> `[1]`을 비워둔 이유: 초기 초안은 `ERROR` 탈출용 리셋 비트를 여기
> 두려 했다. `ENABLE ← 0` 경로로 통일하면서 불필요해졌다.
> 예약 필드로 남긴다. M2 펌웨어 로딩 트리거가 이 자리를 쓸 수 있다.

#### `RING_PROD` — producer index / doorbell (오프셋 `0x002C`, 32bit, RW)

| 비트     | 이름    | 속성 | 리셋값 | 설명                    |
| -------- | ------- | ---- | ------ | ----------------------- |
| `[31:8]` | `RSVD`  | RSVD | `0`    | §4.4                    |
| `[7:0]`  | `INDEX` | RW   | `0`    | 다음에 채울 슬롯 인덱스 |

**NACC-REQ-074** `[HW]` 이 레지스터에 대한 **쓰기가 곧 doorbell**이다.
별도의 doorbell 레지스터는 없다. 쓰기 시점에 아래가 결정된다.

| 현재 상태 | 조건                 | 결과 |
| --------- | -------------------- | ---- |
| `READY`   | `INDEX ≥ RING_SIZE`  | T5   |

| `READY`   | 유효, `prod == cons` | 무시 |
| `BUSY`    | `INDEX ≥ RING_SIZE`  | T12  |
| `BUSY`    | 유효                 | T11  |
| 그 외     | —                    | 무시 |

된다. 판정은 `≥` 비교다 — `RING_SIZE = 128`일 때 유효 범위는 `0`–`127`이다.

**NACC-REQ-076** `[HW]` T2 시점에 디바이스가 이 레지스터를 `0`으로
초기화한다. 이것은 §6.3의 소유권 규칙에 대한 유일한 예외이며,
그 시점에는 진행 중 명령이 없으므로 안전하다.

**NACC-REQ-077** `[HW]` `INDEX`는 명령이 완료될 때마다 1 증가하며

#### `ERR_CODE` — 오류 코드 (오프셋 `0x0040`, 32bit, RO)

| 비트     | 이름   | 속성 | 리셋값 | 설명               |
| -------- | ------ | ---- | ------ | ------------------ |
| `[31:8]` | `RSVD` | RSVD | `0`    | RO 예약. 항상 0    |
| `[7:0]`  | `CODE` | RO   | `0`    | 오류 코드. §8.1 표 |

**NACC-REQ-060** `[HW]` `CODE`는 `ERROR` 진입 시 설정되고, T2가 일어날

## §6. 커맨드 링

### 6.1 디스크립터 포맷

```
offset  size  field       방향        설명
------  ----  ----------  ----------  ------------------------------
0x00     4    opcode      SW → HW     §6.5
0x04     4    flags       SW → HW     리비전 1에서는 예약. 0을 쓸 것
0x08     8    src_addr    SW → HW     소스 버스 주소
0x10     8    dst_addr    SW → HW     목적지 버스 주소
0x18     4    length      SW → HW     바이트 수
0x1C     4    status      HW → SW     완료 시 디바이스가 기록
------
총 크기: 32 바이트
```

**NACC-REQ-030** `[HW]` 디스크립터 크기는 32 바이트로 고정이다.

> 근거: 2의 거듭제곱이므로 인덱스→오프셋 변환이 시프트가 된다.
> 하드웨어 측 어드레스 계산도 단순해진다.

**NACC-REQ-031** `[HW]` `flags`는 리비전 1에서 정의되지 않는다.
디바이스는 이 필드를 읽지 않는다.

**NACC-REQ-032** `[SW]` 드라이버는 `flags`에 0을 써야 한다(MUST).

> 근거: 리비전 2에서 "완료 시 인터럽트"(IOC) 같은 플래그가 여기 들어갈
> 수 있다. 구버전 드라이버가 0을 썼다면 새 하드웨어는 그것을
> "구 동작"으로 해석할 수 있다.

**NACC-REQ-033** `[HW]` `status`는 디바이스가 명령 완료 시 기록한다.
값은 §8.1의 오류 코드와 같은 enum을 쓰며, 성공은 `NONE`(`0x00`)이다.
디바이스는 이 필드를 읽지 않는다.

> **`status` 필드를 넣은 이유:** M1에서는 오류 시 `ERROR` 상태로
> 정지하므로 `ERR_CODE` 하나만으로도 충분해 보인다. 그러나 리비전 2에서
> "오류 명령을 건너뛰고 계속 진행"을 지원하려면 명령별 결과가 필요하고,
> 그때 디스크립터 포맷을 바꾸면 NACC-REQ-008 위반이다.
> 지금 자리를 잡아 두는 편이 싸다.
>
> 부수 효과로 M1에서 디바이스→호스트 writeback 경로를 실제로 만들게
> 되고, NACC-REQ-043의 순서 보장이 검증 대상이 된다.

**NACC-REQ-034** `[HW]` `src_addr`와 `dst_addr`는 **버스 주소**다.
IOMMU 환경에서는 IOVA다.

**NACC-REQ-035** `[HW]` `MEMCPY`의 필드 제약은 아래와 같다.

| 필드                    | 제약                            | 위반 시 오류 코드 |
| ----------------------- | ------------------------------- | ----------------- |
| `src_addr` / `dst_addr` | 4바이트 정렬                    | `BAD_ALIGN`       |
| `length`                | 4의 배수                        | `BAD_LENGTH`      |
| `length`                | `4 ≤ length ≤ 0x100000` (1 MiB) | `BAD_LENGTH`      |

> 근거(정렬): 디바이스는 32비트 워드 단위로 데이터를 이동한다.
> 그래서 길이도 4의 배수여야 한다. v0.2의 `1 ≤ length`는 "4의 배수"와
> 모순이었다.
>
> 근거(길이 상한): 한 명령이 링을 무한정 점유하지 못하게 한다.
> 상한이 없으면 `BUSY` 체류 시간을 드라이버가 예측할 수 없고,
> NACC-REQ-096의 타임아웃 값을 계산할 근거가 없어진다.
>
> `[SW]` 대응: 이 정렬 제약은 dmaengine의 `dma_device.copy_align`과
> 같은 성격이다. 나중에 프레임워크에 편입할 때 그대로 대응된다.

### 6.2 링 제약

**NACC-REQ-036** `[HW]` `RING_SIZE`는 2의 거듭제곱이어야 한다(MUST).
`2 ≤ RING_SIZE ≤ 128`.

> 근거(2의 거듭제곱): 인덱스 순환이 마스크 연산이 된다.
>
> 근거(상한 128): NACC-REQ-038이 링의 연속을 요구한다.
> 128 × 32바이트 = 4 KiB로 정확히 한 페이지에 들어가므로,
> 드라이버는 고차 페이지 할당 실패를 걱정할 필요가 없다.
>
> 근거(하한 2): 1이면 §6.3의 "한 슬롯 비워두기" 규약에 따라
> 사용 가능한 슬롯이 0이 된다.

**NACC-REQ-037** `[HW]` 링 베이스 주소는 32 바이트 경계에 정렬되어야
한다(MUST).

**NACC-REQ-038** `[HW]` 링 전체가 버스 주소 공간에서 연속이어야 한다(MUST).

> `[SW]` 대응: `dma_alloc_coherent()` 한 번의 호출로 얻은 영역을 쓰면
> 이 조건이 만족된다.

### 6.3 인덱스 규약과 필드 소유권

> **이 표가 이 문서에서 가장 중요한 부분이다.**
> 소유권과 순서 규칙은 구조체 정의에 담을 수 없다.

**NACC-REQ-039** `[SW]` 링은 **한 슬롯을 항상 비워둔다**.
`(prod + 1) mod RING_SIZE == cons`이면 링이 가득 찬 것으로 간주하고,
드라이버는 더 이상 `prod`를 전진시켜서는 안 된다(MUST NOT).
사용 가능한 슬롯 수는 `RING_SIZE - 1`이다.

> 근거: `prod == cons`가 empty와 full 양쪽을 뜻하는 모호함을 없앤다.
> 대안이었던 wrap 카운터 방식은 인덱스 폭을 늘려야 하고
> `RING_SIZE`가 8비트인 것과 맞지 않는다.
>
> 이것이 `[SW]` 규약인 이유: §3.3 `READY` 항목 3에 적었듯이
> 하드웨어는 링 full을 검출하지 않는다. 지키지 않으면 조용히
> 데이터가 깨진다.

| 필드 / 인덱스            | 소유자   | 쓰기 가능 시점             | 상대편의 읽기 시점          |
| ------------------------ | -------- | -------------------------- | --------------------------- |
| 디스크립터 `[0x00:0x1C)` | 드라이버 | 해당 슬롯이 free일 때만    | doorbell 관측 이후          |
| 디스크립터 `status`      | 디바이스 | 해당 명령 완료 직전        | `RING_CONS`가 지나간 뒤     |
| `RING_PROD`              | 드라이버 | `READY` / `BUSY` (T2 예외) | doorbell 쓰기 시            |
| `RING_CONS`              | 디바이스 | 명령 완료 시               | 드라이버가 언제든 폴링 가능 |
| `MEMCPY` 목적지 버퍼     | 디바이스 | 명령 실행 중               | `RING_CONS`가 지나간 뒤     |

**NACC-REQ-040** `[SW]` 슬롯은 `RING_CONS`가 해당 인덱스를 지나간 이후에만
드라이버 소유로 돌아온다(MUST).

**NACC-REQ-041** `[SW]` `HALTING`을 벗어난 뒤에는 `[cons, prod)` 범위의
슬롯도 드라이버 소유로 돌아온다. 해당 명령은 폐기된 것이다(NACC-REQ-095).

> `RING_PROD`의 T2 예외는 NACC-REQ-076에 있다. 소유권 표에 예외가
> 있다는 사실 자체를 여기 적어 둔다. 표만 보고 구현하면 놓친다.

### 6.4 가시성

**NACC-REQ-042** `[HW]` 디바이스는 doorbell 쓰기를 관측한 시점에
`[cons, new_prod)` 범위의 디스크립터가 메모리에 유효하다고 가정한다.
드라이버는 NACC-REQ-016을 준수해야 한다(MUST).

**NACC-REQ-043** `[HW]` 디바이스가 `RING_CONS`를 증가시키기 전에
해당 디스크립터의 `status` writeback과 목적지 버퍼 쓰기가 호스트 메모리에
도달하도록 보장한다(MUST).

> 근거: 이 보장이 없으면 드라이버는 `RING_CONS`를 완료 신호로 쓸 수 없다.
> 하드웨어 측 의무를 명시해야 소프트웨어 측 NACC-REQ-018이 충분조건이 된다.
>
> 두 요구사항은 짝이다. 하나만 있으면 반쪽이다.
> **드라이버가 어떤 배리어를 넣든 이 보장을 대체할 수 없다** —
> CPU 쪽에서 고칠 수 없는 문제다.

### 6.5 opcode 목록

| opcode | 이름     | `src_addr` | `dst_addr`  | `length`  | 필드 검증 | 설명                 |
| ------ | -------- | ---------- | ----------- | --------- | --------- | -------------------- |
| `0x00` | `NOP`    | 무시       | 무시        | 무시      | 없음      | 아무 동작 없이 완료  |
| `0x01` | `MEMCPY` | 소스 주소  | 목적지 주소 | 전송 길이 | §6.6      | 호스트 → 호스트 복사 |

**NACC-REQ-044** `[HW]` 정의되지 않은 opcode는 T7을 유발하고
`ERR_CODE ← BAD_OPCODE`가 된다.

**NACC-REQ-045** `[HW]` `NOP`은 `src_addr`, `dst_addr`, `length`를
검증하지 않는다. 어떤 값이든 성공으로 완료된다.

> 근거: 링 메커니즘 자체를 명령 의미론과 분리해서 검증하기 위한
> 명령이다. 검증을 하면 그 목적이 사라진다.

**NACC-REQ-046** `[HW]` `MEMCPY`의 소스와 목적지 영역이 겹치는 경우
결과는 미정의다.

> **`VTD`/`DTV`를 `MEMCPY`로 대체한 이유:** `VTD`는 Intel VT-d(IOMMU)와
> 이름이 충돌한다. 더 중요하게는 두 opcode가 "디바이스 로컬 메모리"를
> 전제하는데 이 문서 어디에도 그 주소 공간이 정의되어 있지 않았다.
> `MEMCPY`(호스트→호스트)는 디바이스 로컬 주소 공간 없이도 DMA 읽기와
> 쓰기 경로를 양쪽 다 검증한다. 디바이스 로컬 메모리는 M2에서
> 펌웨어 로딩과 함께 도입한다(§1.2).

### 6.6 디스크립터 처리 순서

**NACC-REQ-055** `[HW]` 디바이스는 각 디스크립터를 아래 순서로
처리한다(MUST). **검증은 opcode 판별 이후에 한다.**

```
1. 디스크립터 페치 (호스트 메모리 읽기)
     실패 → ERR_CODE ← DMA_FAULT, T7

2. opcode 판별
     NOP      → 5번으로 (검증 없음)
     MEMCPY   → 3번으로
     그 외    → ERR_CODE ← BAD_OPCODE, T7

3. length 검증 (§6.1 NACC-REQ-035)
     실패 → ERR_CODE ← BAD_LENGTH, T7

4. src_addr / dst_addr 정렬 검증
     실패 → ERR_CODE ← BAD_ALIGN, T7
     통과 → 데이터 전송
              실패 → ERR_CODE ← DMA_FAULT, T7

5. status ← NONE writeback
6. writeback이 호스트 메모리에 도달할 때까지 대기 (NACC-REQ-043)
7. RING_CONS ← (RING_CONS + 1) mod RING_SIZE
8. RING_CONS == RING_PROD 이면 T6, 아니면 1번으로
```

> 검증을 opcode 판별 **뒤에** 두는 이유: 순서를 뒤집으면 NACC-REQ-045가
> 무력화된다. `NOP`의 `length`가 0이라는 이유로 `BAD_LENGTH`가 나면
> "링 메커니즘만 따로 검증한다"는 목적이 사라진다.
>
> 구현자가 검증 루틴을 공통 함수로 빼서 opcode 앞에 두기 쉬운 자리다.
> 그래서 순서를 명시적으로 적는다.
>
> T7이 일어나면 6~8번은 실행되지 않는다. `RING_CONS`는 실패한
> 디스크립터를 가리킨 채 남는다(NACC-REQ-078). 단, 실패한 슬롯의
> `status`에는 오류 코드가 기록된다(NACC-REQ-050).

## §7. 인터럽트 모델

### 7.1 벡터 할당

| 벡터 | 이름   | 발생 조건                                                  |
| ---- | ------ | ---------------------------------------------------------- |
| 0    | `nacc` | `(IRQ_STATUS & ~IRQ_MASK)`가 0에서 0이 아닌 값으로 변할 때 |

**NACC-REQ-047** `[HW]` MSI 벡터는 1개다. 완료와 오류는 `IRQ_STATUS`의
비트로 구분한다.

> 근거: M1에는 이벤트 종류가 둘뿐이고, 둘 다 같은 핸들러에서 링 상태를
> 확인해야 한다. 벡터를 나눠도 핸들러가 하는 일이 크게 다르지 않다.
> 나중에 벡터를 늘리면 드라이버 ISR 구조가 바뀐다는 점은 인지하고 있다.

### 7.2 ack 프로토콜

**NACC-REQ-048** `[HW]` `IRQ_STATUS`의 비트는 `RW1C`다. 1을 쓰면
클리어되고, 0을 쓰면 변화가 없다. 읽기만으로는 클리어되지 않는다.

**NACC-REQ-049** `[HW]` 디바이스의 비트 set과 드라이버의 클리어 쓰기가
동시에 일어나면 **set이 이긴다**. 해당 비트는 1로 남는다(MUST).

> 근거: 이벤트를 잃으면 복구할 수 없지만, 이벤트를 중복 관측하는 것은
> 핸들러가 링 상태를 다시 확인하는 것으로 흡수된다.

**NACC-REQ-062** `[SW]` 드라이버는 `IRQ_STATUS`를 읽고, **읽은 값을
그대로 되써서** ack해야 한다(MUST). 읽지 않은 비트를 임의로 1로
써서는 안 된다(MUST NOT).

```c
/* NACC-REQ-062 */
stat = readl(base + NACC_REG_IRQ_STATUS);
if (!stat)
        return IRQ_NONE;

writel(stat, base + NACC_REG_IRQ_STATUS);   /* ack 먼저 */

if (stat & NACC_IRQ_CMD_DONE)
        nacc_handle_completion(nacc);
if (stat & NACC_IRQ_CMD_ERR)
        nacc_handle_error(nacc);

return IRQ_HANDLED;
```

> 근거: 읽은 시점에 1이었던 비트만 1로 되쓰므로, 그 사이 새로 올라온
> 비트에는 0이 쓰이고 → 변화 없음 → 살아남는다.
> `val &= ~BIT` 방식의 read-modify-write는 그 사이 발생한 이벤트를
> 지워버린다.
>
> ack을 처리보다 **먼저** 하는 이유: 처리 도중 발생한 새 이벤트가
> 나중의 ack에 휩쓸리지 않게 한다.
>
> `nacc_handle_error()`가 `ERR_CODE`를 읽을 때 값이 유효한 것은
> NACC-REQ-054가 순서를 보장하기 때문이다.

### 7.3 마스킹

**NACC-REQ-063** `[HW]` `IRQ_MASK`는 **전달만 막는다**. 마스킹된
상태에서도 이벤트가 발생하면 `IRQ_STATUS`의 해당 비트는 세워진다(MUST).

**NACC-REQ-064** `[HW]` 디바이스는 `(IRQ_STATUS & ~IRQ_MASK)`가 0에서
0이 아닌 값으로 전이할 때 MSI를 발행한다(MUST). 이미 0이 아닌 상태에서
다른 비트가 추가로 세워지는 것은 새 MSI를 발행하지 않는다.

**NACC-REQ-065** `[HW]` `IRQ_MASK` 쓰기의 결과로 `(IRQ_STATUS & ~IRQ_MASK)`가
0에서 0이 아닌 값이 되면, 그 시점에 MSI를 발행한다(MUST).

> 즉 마스크를 해제하면 밀려 있던 인터럽트가 즉시 뜬다.
> 이것이 없으면 §3.4의 정지 시퀀스에서 마스킹 후 복구할 때
> 이벤트를 영구히 잃는다. 반대로 이것이 있기 때문에
> NACC-REQ-056(마스크 해제 전 클리어)이 필요하다.
>
> MSI는 edge 성격(posted write)이므로 "레벨이 유지된다"는 개념이 없다.
> 그래서 **전이 조건**으로 정의해야 한다. 조건을 상태로 쓰면
> 인터럽트 폭풍이 나고, 아예 정의하지 않으면 유실이 난다.

**NACC-REQ-066** `[SW]` 드라이버가 `IRQ_STATUS`를 전부 클리어한 뒤
새 이벤트가 발생하면 다시 0 → 0이 아님 전이가 일어나므로 새 MSI를
받는다. 따라서 §7.2의 ISR 관용구는 이벤트를 잃지 않는다.

## §8. 오류 모델

### 8.1 오류 분류

| 코드   | 이름         | 발생 전이 | 복구 가능 | 진행 중 명령의 운명                            |
| ------ | ------------ | --------- | --------- | ---------------------------------------------- |
| `0x00` | `NONE`       | —         | —         | —                                              |
| `0x01` | `BAD_CONFIG` | T3, T10   | 예        | 없음 (아직 시작 전)                            |
| `0x02` | `BAD_PROD`   | T5, T12   | 예        | T5: 없음 / T12: 진행 중 명령 중단              |
| `0x03` | `BAD_OPCODE` | T7        | 예        | 해당 명령 미실행. 이후 명령 미실행             |
| `0x04` | `BAD_LENGTH` | T7        | 예        | 해당 명령 미실행. 이후 명령 미실행             |
| `0x05` | `BAD_ALIGN`  | T7        | 예        | 해당 명령 미실행. 이후 명령 미실행             |
| `0x06` | `DMA_FAULT`  | T7        | 예        | 해당 명령 **부분 실행 가능**. 이후 명령 미실행 |

**NACC-REQ-067** `[HW]` `BAD_OPCODE` / `BAD_LENGTH` / `BAD_ALIGN`은
디스크립터 검증 단계에서 검출되며, 해당 명령의 데이터 전송은
**시작되지 않는다**(MUST). 검증 순서는 §6.6.

**NACC-REQ-068** `[HW]` `DMA_FAULT`는 디스크립터 페치 또는 데이터 전송
도중 호스트 메모리 접근이 실패했을 때 발생한다. 목적지 버퍼의 일부가
이미 갱신되었을 수 있으며, 어디까지 갱신되었는지는 미정의다.

> 검증 오류와 전송 오류를 구분하는 이유: 전자는 목적지 버퍼가 깨끗함이
> 보장되고, 후자는 아니다. 드라이버가 상위 계층에 무엇을 보고할지가
> 달라진다.

**NACC-REQ-069** `[HW]` `DMA_FAULT`의 원인은 IOMMU 변환 실패,
Unsupported Request 응답, 완료 타임아웃을 포함한다. 원인별 세분화는
리비전 1에서 제공하지 않는다.

> 세분화하지 않는 이유: 드라이버의 대응이 모두 같다(링 재초기화).
> 세분화가 필요해지면 `ERR_CODE`의 예약 비트 `[31:8]`을 쓴다.

### 8.2 오류 시 링 상태

- `ERR_CODE`는 T2까지 보존된다 (NACC-REQ-060)
- `RING_CONS`는 실패한 디스크립터를 가리킨 채 고정된다 (NACC-REQ-078)
- `ERR_CODE`와 `STATE`는 `CMD_ERR`보다 먼저 갱신된다 (NACC-REQ-054)

**NACC-REQ-050** `[HW]` T7 발생 시, 실패한 디스크립터의 `status` 필드에
`ERR_CODE`와 같은 값이 기록된다(MUST). 그 이후 슬롯의 `status`는
기록되지 않는다.

> 예외: `DMA_FAULT`가 디스크립터 **페치** 단계에서 발생한 경우
> `status` 기록도 실패할 가능성이 높다. 이 경우 디바이스는 `status`
> 기록을 시도하되, 실패해도 추가 오류를 발생시키지 않는다.
> 드라이버는 `status`가 아니라 `ERR_CODE`를 진단의 정본으로 삼아야 한다.

**NACC-REQ-051** `[SW]` 오류 복구 절차:

1. `STATUS.STATE == ERROR` 확인
2. `ERR_CODE`와 `RING_CONS`를 읽어 원인과 실패 지점을 기록
3. `[0, cons)`의 명령은 성공, `cons`의 명령은 실패,
   `(cons, prod)`의 명령은 미실행으로 상위 계층에 보고
4. §3.4의 정지 시퀀스를 수행 (`ENABLE ← 0` → `HALTING` 탈출 대기 →
   `IRQ_STATUS` 클리어)
5. `INIT`에서 링을 재구성하고 `ENABLE ← 1`
6. `IRQ_MASK` 해제

> 근거: 2번을 4번보다 먼저 하는 이유는 정보를 잃지 않기 위해서다.
> NACC-REQ-060이 T2까지 보존을 보장하므로 순서를 바꿔도 동작은 하지만,
> 명시적인 순서를 두면 드라이버 코드가 단순해진다.
>
> 6번을 5번 뒤에 두는 이유는 NACC-REQ-056이다. 마스크 해제 시점에
> `IRQ_STATUS`가 깨끗해야 유령 인터럽트가 없다.

### Q7. 완료 통지 방식 — MMIO vs in-memory

**상태:** M1은 MMIO(`RING_CONS`)로 확정. M2에서 재검토.

**MMIO 방식의 비용 두 가지**

1. **성능** — `RING_CONS` 읽기마다 PCIe 왕복 지연이 든다.
2. **순서 규칙의 복잡도** — 완료 신호(MMIO)와 데이터(메모리)의 경로가
   달라서, 하드웨어 측에 NACC-REQ-043 같은 명시적 의무가 필요하다.
   in-memory 방식이면 완료 플래그와 데이터가 둘 다 메모리 쓰기라
   PCIe posted write 순서 규칙만으로 순서가 잡힌다.

두 번째가 v0.3에서 추가된 관점이다. 성능만 보고 판단할 문제가 아니다.

**대안:** consumer index를 호스트 메모리에 writeback하는 shadow index.
virtio의 used ring, NVMe의 completion queue가 이 방식이다.

**M1에서 MMIO를 택한 이유:** 더 어려운 케이스를 먼저 다뤄야
NACC-REQ-043 같은 하드웨어 측 의무를 명시하는 훈련이 된다.
그리고 M2에서 방식을 바꾸면 같은 기능의 두 구현을 비교할 수 있다.

**연관:** `libxdma.c`의 `engine_service_wb_monitor` 폴링 경로,
그리고 mainline `xdma.c`가 `CHAN_CTRL_POLL_MODE_WB`를 정의만 하고
쓰지 않는 것과 같은 설계 축이다.

### 단계 4 — 인터럽트

- [ ] `IRQ_MASK` 리셋값이 전부 1인가
- [ ] MSI 발행이 **전이 조건**인가 (REQ-064).

- [ ] `IRQ_MASK` 쓰기 시에도 전이 판정을 하는가 (REQ-065)

### 단계 5 — `HALTING`과 오류 주입

- [ ] `HALTING`에 **의도적 지연을 넣었는가.** 지연이 0이면

      실제 하드웨어에서만 드러나는 버그를 만들게 된다
      (`QEMUTimer` / `timer_mod()`)
- [ ] `HALTING`에서 `RING_CONS`가 폐기 경계로 고정되는가 (REQ-095)
- [ ] `DMA_FAULT` 주입 경로가 있는가. 없으면 §8의 오류 경로를

- [ ] 디스크립터 **페치** 단계의 `DMA_FAULT`도 주입할 수 있는가
